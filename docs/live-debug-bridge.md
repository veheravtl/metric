# Живая диагностика настольного приложения

Мост живой диагностики нужен для совместной отладки без остановки приложения и
ручной упаковки ZIP. Настольное приложение во время работы само оставляет в
`outputs/live_debug` небольшой машинно-читаемый след. Оператор может продолжать
работу, а разработчик или Codex — прочитать состояние, последние события и
изображения того же процесса.

Это локальный файловый мост, а не удалённая телеметрия. Он ничего не отправляет
в сеть и не даёт возможности управлять мышью оператора.

## Как пользоваться

Обычный запуск GUI автоматически открывает новую диагностическую сессию:

```bash
QT_QPA_PLATFORMTHEME=generic QT_STYLE_OVERRIDE=Fusion \
    uv run aerial-mapper-gui
```

Дополнительный флаг не нужен. Пока приложение открыто:

1. воспроизведите проблемный сценарий;
2. если интерфейс выглядит неправильно, нажмите `F12`;
3. сообщите, что произошло и на каком действии, например: «поставил маяк,
   перешёл на следующий кадр, маяк исчез; смотри текущую сессию».

Сбой сопровождения маяков фиксируется автоматически, поэтому F12 для него не
обязателен. Клавиша полезна для визуальной ошибки, которую программа сама не
считает исключением: неправильного масштаба, исчезнувшего маркера или
неожиданного смещения вида.

## Структура файлов

`outputs/live_debug/latest_session.json` — стабильная точка входа. В ней
записаны абсолютные пути к текущей сессии:

```text
outputs/live_debug/
├── latest_session.json
└── sessions/<session-id>/
    ├── events.jsonl
    ├── state.json
    ├── latest-window.jpg
    └── incidents/
        └── 000001-<reason>/
            ├── incident.json
            ├── frame.png
            ├── previous-frame.png
            ├── map.png
            ├── video-view.png
            ├── map-view.png
            └── window.png
```

`latest-window.jpg` обновляется не чаще раза в секунду, уменьшается до ширины
1600 пикселей и нужен только для быстрого взгляда на интерфейс. Полноразмерные
PNG записываются один раз при F12 или автоматическом инциденте, поэтому обычное
перетаскивание маяка не блокируется их кодированием. `previous-frame.png`
появляется только после попытки перехода между кадрами.

`events.jsonl` — последовательность событий в формате JSON Lines: одна
самостоятельная JSON-запись на строку. Приложение сразу сбрасывает каждую строку
на диск, поэтому файл можно читать до закрытия GUI. В нём есть загрузка
источников, смена кадра, запуск и остановка воспроизведения, добавление и
перемещение маяка, успех или срыв сопровождения и необработанные исключения.

`state.json` — полный актуальный снимок состояния. Он содержит текущий кадр,
режимы интерфейса, идентификаторы маяков в модели и обеих Qt-сценах, наблюдения,
запомненные кадры, матрицу совмещения и метрики. Файл записывается через
временную копию и атомарную замену: читатель видит старый или новый целый JSON,
но не половину записи.

При `tracking_failed` событие дополнительно содержит:

- предыдущий и текущий индексы кадров;
- стадию отказа, например `flow_validation`;
- причину и число сохранённых наблюдений;
- для каждого маяка — идентификатор, координаты до и после перехода,
  координату на карте, решение фильтра и ошибку проверки оптического потока
  вперёд–назад.

При `tracking_succeeded` поле `dropped_landmark_ids` перечисляет действительно
удалённые наблюдения, а `excluded_from_alignment_landmark_ids` — сохранённые
маяки, которые геометрический фильтр не использовал в текущей гомографии.
Смешивать эти случаи нельзя: статистический выброс не означает удаление маяка.

Это позволяет отличить три разных случая: маяк исчез из модели, маяк остался в
модели, но исчез только из сцены, или алгоритм перенёс его в недостоверное
место.

## Почему два JSON, а не один лог

Журнал событий отвечает на вопрос «что и в каком порядке произошло», но не
восстанавливает состояние мгновенно без проигрывания всей истории. Снимок
состояния отвечает «что сейчас находится в памяти», но перезаписывает прошлое.
Поэтому нужны оба представления.

PNG исходного кадра отличается от `video-view.png`: первый показывает данные,
переданные алгоритму, второй — фактический вид Qt вместе с маркерами,
масштабом и смещением. Сравнение этих файлов отделяет ошибку математики от
ошибки отображения.

## Ограничения и данные

Мост версии 1 намеренно прост:

- Codex читает файлы по запросу пользователя или во время явно запущенного
  наблюдения; сам факт записи файлов не создаёт автономный фоновый диалог;
- приложение не принимает через мост команды и не меняет состояние по внешнему
  запросу;
- старые сессии пока не удаляются автоматически;
- снимки могут содержать реальные кадры, карту, локальные пути и координаты
  телеметрии.

Каталог `outputs` исключён из Git, но это не делает данные общедоступными или
анонимными. Перед передачей каталога третьим лицам его нужно проверить.

## Основание архитектурного выбора

Схема следует двум устойчивым практикам. Структурированный журнал хранит
стабильные поля события отдельно от человеческого текста, как рекомендует
[модель логов OpenTelemetry](https://opentelemetry.io/docs/specs/otel/logs/data-model/).
Видимые сцены сохраняются штатным механизмом Qt; документация
[QGraphicsView](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QGraphicsView.html)
описывает представление сцены с преобразованием координат и масштабом.

OpenTelemetry как зависимость в первую версию не добавлен: для одного локального
процесса построчный JSON даёт нужную наблюдаемость без сервера-сборщика и
сетевой конфигурации. Если появятся несколько процессов или удалённые рабочие
места, формат событий можно будет подключить к полноценному сборщику отдельно.
